# Prediction Telemetry Model

## 1. Overview

Prediction telemetry is the structured record generated whenever an ML model makes a prediction.

In IntelliCore AI, telemetry connects the prediction layer with the ML monitoring layer. It captures model input, output, model metadata, timestamp, and local explanation so later monitoring components can analyze model behavior.

Current flow:

```text
ML Model
   ↓
Prediction
   ↓
Local SHAP Explanation
   ↓
Telemetry Event
   ↓
FastAPI Ingestion
   ↓
ML Monitoring
   ↓
Important Results / Alerts / Diagnosis
   ↓
Supabase PostgreSQL
```

The current implementation generates telemetry locally. FastAPI ingestion and persistent storage will be implemented later.

---

## 2. Why IntelliCore Needs Telemetry

A single model prediction is not sufficient for monitoring.

IntelliCore needs a stream of prediction events to determine whether:

- input data is changing over time
- model predictions are changing
- prediction distributions are shifting
- model performance is degrading
- model confidence is changing
- calibration is changing
- unusual prediction behavior is occurring
- feature behavior is changing
- model explanations are changing

Therefore, every prediction can be represented as a structured telemetry event.

---

## 3. Telemetry Event Structure

```text
Telemetry Event
│
├── event_id
├── timestamp
├── model
│   ├── model_name
│   └── model_version
│
├── input
│   └── features
│
├── prediction
│   ├── prediction_probability
│   └── predicted_class
│
└── explanation
    ├── method
    └── feature_contributions
```

---

## 4. Event Metadata

### `event_id`

A unique identifier for the prediction event. The implementation generates it using a UUID.

Example:

```text
2d0e12ff-2c68-4d52-a4d4-88c89e29bc3b
```

This allows individual prediction events to be identified during monitoring and diagnosis.

### `timestamp`

The time at which prediction telemetry was generated.

The current implementation uses UTC.

Example:

```text
2026-09-05T15:57:01.354181+00:00
```

Using UTC provides a consistent time reference across services.

---

## 5. Model Information

The `model` section identifies the model that generated the prediction.

```json
{
    "model_name": "xgboost_credit_risk",
    "model_version": "1.0"
}
```

### `model_name`

Identifies the ML workload/model.

Current value:

```text
xgboost_credit_risk
```

This is the representative ML workload currently used for IntelliCore AI.

### `model_version`

Identifies the model version.

Current value:

```text
1.0
```

Model versioning is important because monitoring results must be associated with the correct model version.

## 7. Prediction Information

The `prediction` section contains the output generated by XGBoost.

```json
{
    "prediction_probability": 0.04181474447250366,
    "predicted_class": 0
}
```

### `prediction_probability`

The probability returned by the model for class `1`.

For the current test input:

```text
0.04181474447250366
```

This is approximately 4.18%.

It should be interpreted as the model's predicted probability output, not as a guaranteed real-world probability.

### `predicted_class`

The current predictor converts probability into a binary class using a temporary threshold of `0.50`.

```python
predicted_class = int(probability >= 0.5)
```

Therefore:

```text
Probability = 0.0418
Threshold   = 0.50
Prediction  = 0
```

The threshold is a temporary implementation choice. A production threshold should be selected using validation data and/or an explicit business cost policy.

---

## 8. SHAP Explanation

The telemetry stores the local SHAP explanation for the prediction.

```json
{
    "method": "SHAP",
    "feature_contributions": [
        {
            "feature": "RevolvingUtilizationOfUnsecuredLines",
            "shap_value": 0.3591688573360443,
            "direction": "up"
        }
    ]
}
```

### `method`

Identifies the explanation technique:

```text
SHAP
```

### `feature_contributions`

Contains the contribution of each input feature for this specific prediction.

The current implementation sorts features by absolute SHAP value, so the strongest contributors appear first.

SHAP values represent contributions to the model output relative to the explainer's baseline. They should not be interpreted directly as percentages.

## 11. Implementation

Telemetry generator:

```text
services/ml-monitoring/app/telemetry/telemetry_generator.py
```

Prediction component:

```text
services/ml-monitoring/app/prediction/predictor_02.py
```

The prediction component:

1. loads the XGBoost model
2. validates input features
3. generates prediction probability
4. generates predicted class

The telemetry generator then packages these results with event metadata.

```text
          ↓

          ↓

8. Generate local SHAP explanation
          ↓

          ↓

          ↓

          ↓

```

## 14. Raw Telemetry vs Persistent Storage

IntelliCore AI separates raw telemetry ingestion from durable storage.

Current architecture:

```text
ML Model
   ↓
Telemetry
   ↓
FastAPI
   ↓
Temporary / short-lived raw telemetry
   ↓
Monitoring & Analysis
   ↓
Important Results
   ↓
Supabase PostgreSQL
```

FastAPI acts as the backend/API and ingestion layer. It is not treated as a database.

Raw prediction telemetry is not permanently stored in PostgreSQL in the current architecture.

Important outputs such as:

- monitoring results
- detected anomalies
- alerts
- diagnosis results
- important model-health insights

will be candidates for durable storage in Supabase PostgreSQL.

## 15. Why Telemetry Is Necessary for Monitoring

Telemetry creates the historical evidence required by the monitoring system.

For example:

```text
Event 1 → prediction = 0.04
Event 2 → prediction = 0.07
Event 3 → prediction = 0.03
...
Event N → prediction = 0.72
```

With enough events, IntelliCore can analyze distributions and trends rather than looking at one prediction at a time.

Similarly, input telemetry allows:

```text
Feature distribution
       ↓
Compare current data
       ↓
Compare baseline data
       ↓
Detect drift
```

Prediction telemetry therefore becomes an input to the monitoring engine.

## 16. Current Limitations

The current telemetry generator intentionally has a limited scope.

It currently:

- generates telemetry locally
- creates one event at a time
- uses a fixed model name and version
- uses the temporary 0.50 classification threshold
- does not send events to FastAPI
- does not persist raw telemetry
- does not calculate monitoring metrics
- does not generate alerts
- does not perform drift detection

These capabilities will be implemented later.
